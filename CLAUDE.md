# Мультивалютная учётная система (P&L / CF / Balance) — бриф для разработки

Ты (Claude Code) отвечаешь за реализацию этого проекта с нуля в текущей папке. Прочитай весь файл перед тем, как начинать: он содержит бизнес-требования, архитектурные решения, модель данных и порядок работы. Структуру папок, стек фронтенда в деталях и конкретные библиотеки выбирай сам — ниже даны рекомендации, а не жёсткие ограничения, кроме пунктов, помеченных как решённые.

Заказчик: Kodland. Назначение системы — сбор первичных операций по нескольким юридическим лицам внутри одного аккаунта и автоматическое формирование трёх форм отчётности (P&L, CF, Balance) на базовых принципах IFRS, с мультивалютным учётом на уровне каждой проводки.

## 1. Стек и архитектура (решено)

- Backend: Python, FastAPI, SQLAlchemy, Alembic (миграции), PostgreSQL.
- Auth: JWT, роли на уровне пользователя (см. раздел 3). Допускается использовать Supabase Auth вместо самописного JWT, если это упростит реализацию ролей/RLS — оцени сам, это не жёсткое требование.
- Frontend: веб-интерфейс, взаимодействующий с backend по REST API. Рекомендуется Next.js (React) — он нативно интегрируется с Vercel (см. раздел 12) и даёт готовые preview-деплои на каждый пуш/PR. Внутри — табличный компонент с инлайн- и групповым редактированием (AG Grid / TanStack Table), мастер импорта в несколько шагов, экраны отчётов с переключением валюты. Если решишь выбрать другой стек — обоснуй в README.
- База данных: managed PostgreSQL в Supabase (см. раздел 12) — не разворачивай Postgres в Docker для продакшена/превью, только опционально для локальной разработки при необходимости.
- Локальная разработка: Docker Compose допустим для локального окружения (backend + локальный Postgres), но продакшен/превью идёт через Supabase + Vercel — не дублируй инфраструктуру.
- Мультитенантность на уровне аккаунта: один аккаунт — несколько юридических лиц со своими планами счетов, справочниками аналитики и валютами.

## 2. Роли и доступ (решено)

| Роль | Права |
|---|---|
| Администратор | Юрлица, план счетов, пользователи, справочники, курсы валют |
| Бухгалтер | Ввод/редактирование операций, загрузка реестров, групповое редактирование |
| Вьювер | Только просмотр отчётов |

Роль назначается пользователю глобально и/или в разрезе конкретных юрлиц (доступ можно ограничить списком юрлиц).

Phase 2 (не делать в MVP): роль "утверждающий" + статусы операций (черновик → проверено → утверждено) + блокировка закрытых периодов.

## 3. Юридические лица и мультивалютность (решено)

Юрлицо: наименование, страна, функциональная (локальная) валюта.

У каждой проводки (строки журнала) обязательно хранятся три величины:
1. сумма в валюте операции;
2. сумма в локальной валюте юрлица (пересчёт по курсу на дату операции);
3. сумма в USD-эквиваленте (пересчёт по курсу на дату операции).

Курсы валют подгружаются автоматически из внешнего источника на дату операции (реализуй pluggable-провайдер: например CBR XML API для рублёвых пар + универсальный fallback-провайдер типа exchangerate.host/open.er-api.com для остальных валютных пар — оба без ключа API). Курсы сохраняются в таблице `fx_rates` (date, currency_from, currency_to, rate, source) с возможностью просмотра и ручной корректировки администратором.

Для баланса при пересчёте иностранных операций применяй логику IAS 21: операции P&L — по курсу на дату операции, статьи Balance — по курсу закрытия периода (последний известный курс на конец периода). Зафиксируй это явно в движке отчётов, а не только на уровне проводки.

Во всех отчётах пользователь может переключать валюту отображения: локальная валюта юрлица ↔ USD.

## 4. План счетов (решено)

- Гибкий иерархический план счетов (счёт → подсчета), с типом счёта (актив/обязательство/капитал/доход/расход) и явным маппингом каждого счёта на строку P&L/CF/Balance.
- Обязательна поддержка импорта существующего плана счетов из CSV/Excel (типичный кейс — выгрузка из 1С) с сохранением текущих кодов и структуры, плюс UI для донастройки/добавления счетов вручную после импорта.
- У каждого юрлица свой план счетов; при создании нового юрлица должна быть возможность скопировать/использовать существующий план как шаблон.

## 5. Аналитика операций (решено)

К каждой строке операции, помимо счёта и юрлица, можно привязать: центр затрат/подразделение, контрагент, проект. Справочники редактирует администратор, значения — в разрезе юрлица.

## 6. Загрузка реестра операций (решено)

Мастер импорта Excel/CSV, шаги:
1. загрузка файла;
2. сопоставление колонок файла с полями системы (дата, счёт, сумма, валюта, юрлицо, аналитика и т.д.) — пользователь настраивает сопоставление сам;
3. сохранение шаблона сопоставления для повторного использования (разные источники — банк, 1С — имеют разные шаблоны);
4. предпросмотр и валидация (баланс дебет/кредит, обязательные поля, распознаваемость валюты/счёта) с понятными сообщениями об ошибках;
5. подтверждение и запись в журнал операций как `ImportBatch`, с привязкой каждой созданной операции к батчу.

## 7. Редактирование операций (решено)

- Редактирование отдельной операции (все поля).
- Групповое (bulk) редактирование выбранного набора операций (например, массовая замена контрагента / центра затрат / счёта).
- Базовый журнал изменений (`audit_log`: кто, когда, какое поле, старое/новое значение) — обязателен в MVP. Полноценные статусы согласования — Phase 2 (см. раздел 2 и 9).

## 8. Отчётность (решено)

Три формы, каждая — за произвольный период по выбору пользователя (не жёстко месяц/квартал/год — произвольный диапазон дат):

- **P&L** — по методу начисления, из оборотов по счетам доходов/расходов;
- **CF** — прямой метод (по видам поступлений/выплат), с разбивкой на операционную/инвестиционную/финансовую деятельность;
- **Balance** — по остаткам счетов на конец периода.

Каждый отчёт: интерактивный экранный просмотр + выгрузка в Excel (openpyxl/xlsxwriter) и PDF (weasyprint/reportlab), с переключением валюты (локальная ↔ USD).

Групповой вид (по всем юрлицам аккаунта): простое суммирование показателей юрлиц **без элиминации** внутригрупповых операций (решение по консолидации на этом этапе), при сохранении возможности посмотреть отчётность каждого юрлица отдельно. Полная консолидация с элиминацией — Phase 2.

## 9. Фазы разработки

### MVP (сделай в первую очередь, это определение готовности для сдачи):
- Учёт по нескольким юрлицам в одном аккаунте;
- Гибкий план счетов с импортом из CSV/Excel;
- Мультивалютность (3 суммы на проводку, автозагрузка курсов, ручная корректировка);
- Мастер импорта реестра операций с сопоставлением колонок и сохранением шаблонов;
- Редактирование операций, включая групповое, с базовым журналом изменений;
- Три отчёта (P&L, CF прямой метод, Balance) за произвольный период, с переключением валюты и экспортом в Excel/PDF;
- Роли admin/accountant/viewer с ограничением доступа по юрлицам;
- Групповой отчёт по всем юрлицам без элиминации;
- Ручной ввод входящих остатков на 01.01.2025 по каждому юрлицу как точка старта учёта;
- Docker Compose для локального запуска, README с инструкцией по установке, seed-скрипт с демо-данными (2-3 юрлица, разные валюты, десятки операций) для проверки работоспособности.

### Phase 2 (после сдачи MVP, зафиксируй в README как roadmap, не реализуй сейчас):
- Воркфлоу утверждения операций (статусы черновик/проверено/утверждено, блокировка закрытых периодов);
- Полная консолидация с элиминацией внутригрупповых операций, взаимных остатков и нереализованной прибыли.

## 10. Модель данных (укрупнённо, детали — на твоё усмотрение при проектировании миграций)

- `accounts` (аккаунт-тенант), `legal_entities` (юрлицо: name, country, functional_currency)
- `users`, `roles`, `user_entity_roles` (пользователь ↔ роль ↔ юрлицо)
- `currencies`, `fx_rates` (date, currency_from, currency_to, rate, source)
- `chart_of_accounts` / `accounts_coa` (иерархия счетов, тип счёта, IFRS-маппинг, привязка к юрлицу)
- `cost_centers`, `counterparties`, `projects` (справочники аналитики, привязка к юрлицу)
- `journal_entries` (шапка операции: юрлицо, дата, описание, создатель) и `journal_lines` (строка: счёт, аналитика, transaction_currency, transaction_amount, local_currency_amount, usd_amount, fx_rate_to_local, fx_rate_to_usd)
- `import_batches`, `import_mapping_templates`
- `audit_log` (entity_type, entity_id, field, old_value, new_value, changed_by, changed_at)
- `opening_balances` (юрлицо, счёт, дата, сумма) — для стартовых остатков на 01.01.2025

## 11. Критерии готовности MVP

1. Можно создать 2+ юрлица с разными функциональными валютами внутри одного аккаунта.
2. Можно импортировать/задать план счетов для каждого юрлица (включая импорт из CSV).
3. Можно загрузить реестр операций из Excel/CSV через мастер импорта с сопоставлением колонок; результат проходит валидацию баланса.
4. Каждая проводка после импорта/ввода вручную имеет все три суммы (валюта операции, локальная, USD), рассчитанные по курсу на дату операции.
5. Можно отредактировать операцию (в т.ч. массово выбранную группу операций) и увидеть, что изменение отражено в журнале изменений.
6. Можно сформировать P&L, CF (прямой метод) и Balance за произвольный период для одного юрлица и в групповом (суммарном) виде, с переключением локальная валюта/USD, и выгрузить каждый отчёт в Excel и PDF.
7. Роли admin/accountant/viewer реально ограничивают действия в UI и API (проверяется тестами).
8. `docker-compose up` разворачивает всё окружение с нуля и сидирует демо-данные, на которых видно, что баланс (Assets = Liabilities + Equity) сходится.

## 12. Деплой для промежуточной проверки (превью-окружение) — решено

Заказчик хочет **постоянную ссылку**, открываемую с любого устройства, которая обновляется после каждого значимого этапа. У заказчика уже есть аккаунты GitHub, Vercel и Supabase — используй именно эту связку, отдельный VPS не нужен.

**Схема:**
1. **GitHub** — репозиторий проекта. Каждый коммит/пуш в основную ветку триггерит автодеплой.
2. **Supabase** — управляемый PostgreSQL для всех окружений (dev/preview/prod). Для подключения из serverless-функций Vercel используй **пуловый (pgbouncer/transaction pooler) connection string** Supabase, а не прямой — иначе при параллельных вызовах серверлесс-функций быстро закончатся доступные подключения к БД. При необходимости — используй Supabase Storage для хранения загруженных файлов импорта.
3. **Vercel** — хостинг frontend (Next.js) и, если решишь разместить backend там же, Python-функций FastAPI через ASGI-адаптер. Подключи GitHub-репозиторий к Vercel — это даёт: постоянную продакшен-ссылку вида `<project>.vercel.app`, которая обновляется автоматически на каждый пуш в main, и отдельную preview-ссылку на каждый PR/ветку для промежуточной проверки без влияния на основную.

**Важные технические ограничения serverless (Vercel), учти при реализации:**
- Ограничение времени выполнения функции (обычно секунды, до ~60 сек на платных планах) — не делай синхронный импорт очень больших файлов одним запросом; читай/валидируй файл потоково и/или обрабатывай крупные реестры батчами.
- Для генерации PDF используй **reportlab**, а не weasyprint — у weasyprint системные зависимости (Pango/Cairo), которые плохо переносятся в serverless-среду.
- Автозагрузку курсов валют реализуй через **Vercel Cron Jobs** (`vercel.json` → `crons`), дёргающие эндпоинт обновления курсов раз в день, а не через фоновый процесс/scheduler внутри приложения.
- Функции stateless и без постоянного диска — не рассчитывай на локальные файлы между вызовами, только БД/Storage.

Если backend на Vercel окажется неудобен для конкретной задачи (например, тяжёлые батчевые импорты) — можно вынести только backend на отдельный сервис (Render/Railway/Fly.io) при сохранении frontend на Vercel и БД на Supabase; сообщи об этом пользователю как о решении, а не принимай его молча.

После каждого значимого этапа/шага из раздела 9 и 11 — запушь в GitHub и явно сообщи пользователю ссылку (production или preview) и что именно там можно проверить.

## 13. Прочее

- Базовая валюта представления группового отчёта — USD, но с переключением на локальную валюту любого выбранного юрлица.
- Не закладывай в MVP авторизацию через внешние SSO — простой email/пароль + JWT достаточно.
- Пиши тесты хотя бы на: расчёт мультивалютных сумм, движок отчётов (сходимость баланса на демо-данных), права доступа ролей.
